FAIL: 오류 경로에 키의 파일·stderr 유출이 남아 있고, 연결 중단의 처리 불명 집계와 핵심 시험이 요구사항을 충족하지 못한다.

## 지적 목록

계획 4절·7절을 요구사항으로 삼아 지정 파일과 diff를 검토했다. `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests`는 Python 3.15.0에서 150개 모두 통과했다. 아래 재현과 변이는 가짜 키·대역 opener·메모리상의 소스 사본만 사용했다. 저장소 구현과 시험 파일은 수정하지 않았다.

1. **심각도: 높음: 응답 검증 오류는 파일로, 재개 검증 오류는 stderr로 키를 유출한다.**

   - **위치:** `skills/founder-consumer/jev.py:201`, `:733`, `:743`, `:797`, `:810`, `:858`; `docs/DESIGN.md:108`.
   - **문제:** `check_reply()`는 잘못된 `model`·확률·choice 등의 값을 오류 문자열에 그대로 넣는다. 전송 루프는 이 문자열을 `runs[].stopped`에 넣고 `_save()`한다. `main()`의 마스킹은 stderr 출력에만 적용되므로 파일 저장을 보호하지 못한다. 재개에서는 `check_saved()`가 키 수집보다 먼저 실행된다. 이 단계에서 잘못된 저장값을 출력하면 `main()`의 `keys`가 비어 있어 stderr도 마스킹하지 못한다. 계획 4.9와 DESIGN의 “키는 출력·파일·예외 어디에도 쓰지 않는다”에 어긋난다.
   - **제안:** 검증 오류에 응답의 원문 값을 넣지 않고 필드명·위반 조건만 남긴다. 오류를 예외·이력·출력으로 내보내기 전에 동일한 마스킹 경계를 적용한다. 키를 읽지 않는 재개 사전 검사에서도 외부 입력값을 그대로 출력하지 않도록 한다. HTTP 오류 본문뿐 아니라 200 응답 검증과 저장 파일 검증에도 유출 회귀 시험을 추가한다.
   - **확인한 방법:** 대역의 200 JSON에서 `model`을 가짜 키로 반환했다. 종료 코드 2, stdout·stderr 유출 없음, **`jev.json`의 `runs[0].stopped`에는 가짜 키가 그대로 저장됨**을 확인했다. 별도 임시 패널의 저장 답 `jev.model`을 가짜 키로 바꿔 재개하자, 호출 0건·종료 코드 2인데 **stderr에 가짜 키가 출력됐다**. 실제 키 파일은 접근하지 않았다. 기존 `tests/test_jev.py:843`은 HTTP 401·503·URLError 경로만 검사하여 이 두 경로를 놓친다.

2. **심각도: 중간: `URLError`로 감싼 연결 중단은 처리 불명 건수에서 빠진다.**

   - **위치:** `skills/founder-consumer/jev.py:403`, `:420`; `tests/test_jev.py:734`.
   - **문제:** `URLError`에서는 원인이 타임아웃일 때만 `unknown`을 올린다. 요청 송신 중의 `ConnectionResetError`·`BrokenPipeError`도 urllib에서 `URLError`로 감싸질 수 있다. 이 경우 재시도하면서 `checkpoint(False)`로 `inflight`까지 지우므로, 서버 처리 여부가 불명인데도 이력과 비용 안내에서는 사라진다. 계획 4.9의 “요청을 보낸 뒤 응답 전에 끊긴 모든 경우” 집계에 어긋난다.
   - **제안:** 명백한 요청 전 실패와 송신 도중 또는 이후일 수 있는 실패를 구분한다. 후자의 reset·broken pipe 등은 보수적으로 `unknown`에 포함한다. 감싸지 않은 `RemoteDisconnected`뿐 아니라 `URLError(ConnectionResetError(...))`와 `URLError(BrokenPipeError(...))`도 시험한다.
   - **확인한 방법:** 첫 요청에서 `URLError(ConnectionResetError(54, ...))`를 발생시키고 이후 정상 응답을 반환했다. 카드 10장에 대해 성공 종료, 시도 11회·재시도 1회였으나 **`unknown=0`**이었다. 로컬 표준 라이브러리의 `AbstractHTTPHandler.do_open()`이 요청 중 `OSError`를 `URLError`로 감싸는 코드도 확인했다. 실제 연결은 사용하지 않았다.

3. **심각도: 중간: 고정 요청 내용과 seed 규칙의 결함을 시험이 검출하지 못한다.**

- **`tests/test_jev.py:721`부터 `:727`까지의 기본 urllib 리다이렉트 시연 블록.** 표준 라이브러리 opener가 다른 호스트로 키를 전달함을 다시 증명하는 부분이다. 제품의 opener가 302를 거부하고 후속 요청을 만들지 않는 검사는 `:728` 이후에 남는다. 시험 소스 사본에서 이 블록만 삭제해도 Jev 65개가 모두 통과했다. 그 사본에 `_NoRedirect` 제거 변이를 넣으면 여전히 해당 시험 하나가 실패했다. 삭제해도 이번에 확인한 제품 결함 검출력은 유지된다.

## 확인하지 못한 것

- 실제 TypeSafe API의 현재 응답 형식·최종 틀의 예측 결과·실제 지연·청구액은 확인하지 않았다. 네트워크 호출, 실제 키 파일 접근, 비용 발생은 하지 않았다.
- Python 3.8 실행 환경에서는 돌리지 않았다. `jev.py`, 변경된 `panel.py`, `test_jev.py`는 현재 Python의 `ast.parse(..., feature_version=(3, 8))` 구문 검사를 통과했다. import와 사용 API의 정적 검토에서 외부 패키지 의존이나 명백한 3.8 비호환은 발견하지 못했지만, 이는 3.8 런타임 검증을 대체하지 않는다.
- 실제 SIGKILL·디스크 장애는 재현하지 않았다. 교체 전후의 중단·재개는 기존 대역 시험으로 확인했다.

확인된 보존 범위: `panel.py` diff는 `tally()`의 폴더 인자와 해당 경로 사용 두 줄뿐이다. 기본 경로와 빈 이유 문자열 보존, 에이전트 파일의 바이트 불변, 판정의 구매율 25% 미만·경계 사례는 회귀 시험을 통과했다. `compile.py:118`은 계속 `panel/results.json`만 읽는다. `van_westendorp.py`는 변경되지 않았고, Jev의 `read → analyse → report` 연결·통화·5장 미만 처리·검열 및 보정 안내 시험도 통과했다. 지문, 디렉터리 상태, 응답 검증, 원자적 교체, 재개, 리다이렉트 거부, 재시도 및 추정 예산은 소스와 기존 시험을 대조했으며, 위 지적 외의 위반은 확인하지 못했다. 문서 diff의 판정 분리·출력 위치·외부 전송 안내는 구현과 일치하며, 키 비유출 보장은 지적 1과 충돌한다.
