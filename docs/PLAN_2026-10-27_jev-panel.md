## 1. 결론

`founder-consumer`에 새 파일 `jev.py`를 더한다. Jev는 **판정에 들어가지 않는 별도 층**이다. 에이전트 패널(`answers/`, `results.json`, `compile.py` 판정)은 지금과 완전히 같다. Jev는 같은 카드나 더 많은 카드(200~500장)에 대해 구간·행동·소득별 구매율, 확률 상위 카드 표, 구매 이유 분포, 가격 곡선(탐색 추정)을 몇십 초에 만들어 `jev-answers/`와 `jev-results.md`에 따로 쓴다.

시간이 주는 곳: 창업자가 판정용 에이전트 패널을 20명(`--quick`)으로 두고, 폭은 Jev 200장으로 채운다. 100명 에이전트 패널(10회 웨이브)이 2회 웨이브와 Jev 약 1분으로 바뀐다. 판정의 구매율은 에이전트 20명에서 나오므로 100명 에이전트 패널보다 거칠다. 이것이 거래 조건이다. 100명 에이전트의 판정 정밀도를 원하면 Jev는 도움이 안 된다.

Jev가 못 하는 것: 구매자 말투의 인용문, 같은 제품의 작은 오퍼 차이, 절대 구매율.

## 3. Jev (설계에 필요한 만큼만)

- `POST https://api.typesafe.ai/v1/systemone`, `Authorization: Bearer <키>`, `Content-Type: application/json`. 본문 `model`, `state`, `questions`.
- `noul`(예/아니오 확률), `choice`(보기 1~255개, 확률 분포, confidence), `score`(2~10단계 설명, 단계별 확률, 기댓값). 한 요청의 질문들은 같은 상태를 놓고 **서로 독립적으로** 판단된다(공식 문서). 이유 질문은 구매 질문의 결과를 보지 못한다. 질문 ID는 모델에 전달되지 않는다.
- 글을 쓰지 않는다. 숫자 계산·세기에 약하다. choice는 첫 보기에 쏠린다. 상태 안의 무관한 내용이 답을 흔든다. 문서는 영어 정확도가 가장 높다고 적었다.
- 한도: 요청당 64k 토큰, 질문당 32k. 입력 토큰 100만 개당 $0.042, 출력 무료. 429/529는 백오프 재시도(공식). 요금 한도는 조직별.
- 별칭 `jev-latest`는 답이 바뀔 수 있다. `jev-1.14.0`을 고정한다. 같은 요청도 실행마다 조금 다르다(2.1).

### 4.3 요청(카드 1장 = 요청 1건, 틀 버전 `v1`, 실행 뒤 바꾸지 않는다)

`state`(고객 언어 그대로):
- `who_decides`: 이름, 나이, 구간, 연 소득(`money()` 표기), 구매 방식과 설명, 하루 맥락, 첫 의심, `target`, 고정 문장 "Most people do not buy most things. Decide with this person's own money, habits and doubts in a normal week."(에이전트 브리프의 "맞장구치지 마세요"에 해당하는 보정 손잡이).
- `offer_seen_for_the_first_time`: 피치 원문.

`questions`(영어, 고정):
1. `buys` (noul): "After seeing `offer_seen_for_the_first_time` once, would `who_decides` start paying for {paid} at {money} {unit} within the first month? Yes only if they would actually pay, not just use a free tier or a free trial."
2. `reason_code` (choice 9개): "When `who_decides` weighs whether to pay for {paid}, which of these matters most?" 보기 설명은 영어 한 줄씩(코드 그대로). 구매 결정을 전제하는 문구("decision to pay or not pay")는 쓰지 않는다(독립 판단이므로). 보기 순서는 `random.Random("%d:%s" % (seed, card_id))`로 카드마다 섞는다. 처리 순서나 건너뛴 카드 수와 무관하게 같은 카드는 같은 순서다.
3. 가격 12개 (score 5단계): "If the price of {paid} were {money_k} {unit}, how would `who_decides` feel about that price?" 단계: "too cheap to be any good (quality doubt) / a bargain / about right, a fair price / getting expensive, but might still buy / too expensive, would not buy".

사다리: `--price` × [0.2, 0.3, 0.45, 0.6, 0.8, 1.0, 1.25, 1.6, 2.0, 2.5, 3.3, `--ladder-max`(기본 5.0)]. 1.0배 지점은 `--price` 그대로 두고, 나머지 값은 유효숫자 2자리로 다듬는다(실수 유지, 정수 변환 없음. 6.5달러 × 0.2 = 1.3. 14,900원이면 3,000 / 4,500 / 6,700 / 8,900 / 12,000 / 14,900 / 19,000 / 24,000 / 30,000 / 37,000 / 49,000 / 75,000). 입력 검증: `--price`는 양의 유한수. `--ladder-max`는 유한수이고 3.3보다 커야 한다. 다듬은 사다리는 모두 양의 유한수이고 **엄격한 오름차순**이어야 한다. 아니면 거부한다.

구매 횟수 질문과 의심(`objection`) 질문은 넣지 않는다. Jev 답에는 `purchases_first_month`가 없고(`tally`의 평균은 None 처리됨), `objection`·`reason`·`would_change_my_mind`는 빈 문자열이다.

### 4.4 응답 검증(Jev 경계. `_answer_ok`와 별도. 재개 때 읽는 파일에도 같은 검사)

- `answers`에 보낸 질문 ID가 모두 있고 각 `type`이 보낸 것과 같다.
- 모든 확률 성분(noul 값, choice `probabilities` 값, score `probabilities` 값)은 숫자 타입이고 유한하며 0 이상 1 이하.
- choice: `choice`가 보낸 보기 안에 있고 `probabilities`의 키 집합이 보기 집합과 같으며 합이 1±0.03.
- score: `probabilities` 키가 정확히 `"0"`~`"4"`, 합이 1±0.03. (오차 0.03인 이유: Jev는 확률을 소수 둘째 자리로 돌려주고 score는 5단계라 반올림 오차가 최대 0.025까지 쌓인다. 2026-10-27 실제 응답 760개 중 30개가 정확히 0.01 경계였다. 구현 검수에서 발견.)
변환 뒤 답은 `panel._answer_ok`를 통과해야 하고 가격 4개는 양의 유한수다.

### 4.5 변환(`jev-answers/Pxxx.json`)

기존 답 키(`id`, `buys`, `reason_code`, `reason:""`, `objection:""`, `would_change_my_mind:""`, `price_*` 4개)와 `jev` 블록(`model`, `p_buy`, `reason_probabilities`, `price_probabilities`(사다리별 5개), `input_tokens`, `fingerprint`, `convert_version`, `flags`). 원본 확률을 남기므로 재호출 없이 다시 변환할 수 있다.

- `buys = p_buy >= 0.5`.
- 가격: 사다리 오름차순에서 곡선 4개를 만든다. P0 = P(너무 싸다), C1 = P0 + P(싸다), E = P(비싸다) + P(너무 비싸다), T = P(너무 비싸다).
  - 내림 교차(`price_too_cheap` ← P0, `price_cheap` ← C1): 곡선이 **처음으로** 0.5 미만이 되는 지점 i. i가 0이면 아래쪽 검열, 값은 사다리 최저. 없으면 위쪽 검열, 값은 사다리 최고. 그 밖은 i-1과 i 사이 선형 보간.
  - 오름 교차(`price_expensive` ← E, `price_too_expensive` ← T): 곡선이 **처음으로** 0.5 이상이 되는 지점 i. i가 0이면 아래쪽 검열(사다리 최저). 없으면 위쪽 검열(사다리 최고). 그 밖은 보간.
  - 정확히 0.5는 "이상"으로 센다.
  - 플래그 두 가지를 따로 둔다. `flags.multi_cross`: 0.5를 두 번 이상 지난 곡선 이름. `flags.nonmonotone`: 인접 점이 기대 방향(내림 곡선은 감소, 오름 곡선은 증가)을 0.05 넘게 어긴 곡선 이름. 복수 교차 없이도 비단조일 수 있다(예: 0.9, 0.7, 0.8, 0.4).
  - 순서 보정: `cheap = max(cheap, too_cheap)`, `expensive = max(expensive, cheap)`, `too_expensive = max(too_expensive, expensive)`. 바뀌었으면 `flags.clamped = true`. 가격 도구는 같은 값을 허용한다(`van_westendorp.py:129`, `<=`).
  - 검열값은 경계값으로 저장하고 `flags.censored`에 어느 곡선이 어느 쪽인지 적는다. 저장하는 이유: "너무 싸다"의 아래쪽 검열은 흔하다(2.3). 그 카드를 제외하면 가격 분석에 남는 카드가 너무 적다. 편향의 방향은 곡선과 검열 쪽에 따라 다르므로 단정하지 않는다. `jev-results.md`의 가격 절은 곡선별 검열 수와 보정 수를 같은 자리에 붙이고 "경계값 대입에 따른 탐색 추정"이라고 제목에 적는다. 위쪽 검열이 카드의 25%를 넘으면 "`--ladder-max`를 올려라"를 출력한다.

### 4.6 `panel.py` 변경(한 가지)

`tally(d, answers="answers")`: 답 폴더 이름을 인자로 받는다. 기본값이면 지금과 같다. `jev.py`가 `tally(d, answers="jev-answers")`로 구간·행동·소득 분해와 이유별 인원수를 재사용한다. `why_not`·`why_yes`의 인용문 목록은 Jev 경로에서 쓰지 않는다(`jev.py`가 인원수만 쓴다). 빈 인용문 필터는 넣지 않는다(기본 경로에서 `reason: ""`인 에이전트 답은 `_answer_ok`상 유효하므로 출력이 바뀔 수 있다. 2회차 R2-7).

`results_md`, `write_briefs`, `check`, `status`, `save`, `_answer_ok`, `_write_json`은 손대지 않는다.

### 4.7 출력

- `jev-answers/Pxxx.json`: 4.5.
- `jev.json`: 두 부류를 구분해 저장한다.
  - 파생값(매 실행 시작 때 `jev-answers/`에서 다시 계산): 완료 카드 수, 성공 입력 토큰 합과 달러 추정, 검열·보정·복수 교차·비단조 수.
  - 보존값(실행마다 덧붙이고 다시 계산하지 않음): `fingerprint`, `settings`(모델, 가격, paid, unit, 사다리, 통화, seed, 틀 버전, 변환 버전), 실행 이력 목록(시작·끝 시각, 시도 수, 재시도 수, 타임아웃 수, 처리 여부 불명 수, 그 실행의 확인 비용, 중단 사유).
  - `inflight`: 요청을 보내기 직전에 카드 ID를 기록하고 파일 저장 뒤 지운다. 다음 실행이 `inflight`를 발견하면 "처리 여부 불명" 1건으로 이력에 옮기고 그 카드는 다시 보낸다.
- `jev-results.md`와 `jev-results.json`:
  1. 머리글: 모델, 판정 기준 0.5, 카드 수, 평균 확률과 "비율이 아니다" 문장, 인용문 없음 안내, 이유는 "구매와 독립으로 판단된 주요 고려 요인"이라는 문장.
  2. `panel.tally(d, answers="jev-answers")`의 구간·행동·소득 분해 표.
  3. 이유 분포 표: 전체 카드 기준 인원수. 구매·미구매로 나눈 교차표를 함께 두되 "독립 예측의 교차표"라고 표시한다.
  4. 확률 상위 카드 표: `p_buy` 상위 10장(ID, 확률, 구간, 행동).
  5. 가격 절(탐색 추정): `read(jev-answers) → analyse → report(price=--price)`. `--price`를 넘겨 "현재 가격이 범위 안/밖" 줄이 나온다. 완전한 답이 5장 미만이면 `analyse`가 실패하므로 이 절만 "표본 부족(N장)"으로 쓰고 나머지 절은 그대로 낸다. 가격 분석 실패가 답을 무효화하거나 재호출하게 하지 않는다. 통화는 `jev.json`의 `settings`에서 직접 넘긴다. 표 아래에 곡선별 검열(아래/위)·보정·복수 교차·비단조 수를 붙인다.
  6. 일치표: `--dir`의 `answers/`에 유효한 에이전트 답이 있는 카드에 대해 2×2 표(둘 다 구매 / 에이전트만 / Jev만 / 둘 다 아님, 분모 n). 에이전트 답이 0건이면 `agreement: null`이고 절을 생략한다. 한 숫자의 "일치율"은 쓰지 않는다.
- 두 집계(분해 표와 가격 절)는 같은 파일 집합(현재 카드 ID의 `jev-answers/` 파일)을 쓴다.

### 4.8 지문, 재개, 원자적 쓰기

- 지문: 키 없이 정규화한 객체를 `json.dumps(obj, sort_keys=True, ensure_ascii=False, separators=(",", ":"))`로 직렬화해 sha256. 객체에는 실제 요청 `state`에 들어가는 카드 필드 전체(모든 카드), 피치 원문, `target`, 통화, seed, 모델, 틀 버전, 변환 버전, 사다리, `paid`, `unit`, 보기 설명을 넣는다. 요청은 이 지문을 만든 같은 스냅샷에서 만든다. 같은 ID의 소득·행동만 바뀌어도 지문이 달라진다.
- `run` 시작: `jev.json`이 있으면 지문을 비교한다. 다르면 "설정이나 카드가 바뀌었다. 새 `--dir`을 쓰거나 `jev-answers/`와 `jev.json`을 직접 지워라"를 출력하고 종료 코드 2. 자동으로 지우지 않는다. 없으면(그리고 4.2의 상태 검사를 통과하면) `jev.json`을 먼저 쓴다.
- 카드 파일은 `path + ".tmp"`에 쓰고 `os.replace`로 바꾼다(`jev.py` 안에서. `panel._write_json`은 고치지 않는다). `jev.json`도 같은 방식으로 카드마다 갱신한다. 2026-10-28 보안 검토 뒤로는 고정 이름 대신 `mkstemp`로 새로 만든 임시 파일에 쓴다(`docs/PLAN_2026-10-27_jev-sweep.md` 13절).
- 재개: `jev-answers/`의 모든 파일을 먼저 4.4·4.5 기준으로 검사한다(지문과 변환 버전 일치, 형식). 유효한 카드는 보내지 않는다. 손상·불일치 파일은 카드 ID를 출력하고 멈춘다. 덮어쓰지 않는다.
- `answers/`(에이전트), `panel.json`, `personas.json`, `results.*`는 읽기만 한다. 바이트 하나 바꾸지 않는다.

### 4.9 전송, 재시도, 비용, 키

- 리다이렉트를 따르지 않는 opener(`HTTPRedirectHandler` 대체)를 쓴다. 3xx는 오류로 멈추고 후속 요청을 보내지 않는다. 이유: `urllib`은 다른 호스트로의 리다이렉트에도 `Authorization`을 그대로 넘긴다(2026-10-27 로컬에서 확인).
- 시도당 시간 제한 60초. 재시도 대상: 429, 529, 502, 503, 504, `URLError`(DNS·연결·TLS·타임아웃). 최대 추가 5회, 대기 min(2^k, 30)초 + 0~1초 무작위. `Retry-After`가 있으면 숫자형은 그 초(최대 60), HTTP 날짜형은 현재 시각과의 차(최대 60), 해석 불가면 무시. 400·401·403·404·413·422는 재시도 없이 멈춘다(종료 코드 2). 200인데 JSON이 깨졌거나 4.4 검증에 실패하면 재시도 없이 멈춘다.
- 처리 여부 불명: 요청을 보낸 뒤 응답을 받기 전에 끊긴 모든 경우(타임아웃, 연결 끊김, 프로세스 중단)를 센다. `URLError`로 감싸인 경우도 같다. 요청 전 실패가 분명한 `ConnectionRefusedError`와 DNS 실패(`socket.gaierror`)만 불명에서 뺀다. 재시도는 하되 이력에 남긴다. 과금 여부는 모른다.
- 오류 출력: 상태 코드와 본문 앞 300자. 본문에서 키 문자열을 지운 뒤 출력한다. 키는 로그·파일·예외 메시지 어디에도 쓰지 않는다. 응답 검증 오류 문자열에는 응답의 원문 값을 넣지 않는다(필드명과 위반 조건만). `jev.json`의 `stopped`와 stderr에 쓰기 전에 같은 키 제거 경계를 거친다. 재개 경로의 저장 파일 검증도 같다(구현 검토 1회차 지적 1).
- 비용과 예산: `--budget-usd`(기본 1.00)는 추정 기반 중단선이지 청구액 상한이 아니다. 다음 요청을 보내기 전에 "이번 실행의 확인 비용 + 직전 카드 토큰 기준 다음 카드 예상"이 예산을 넘으면 멈춘다. 첫 카드 뒤 "남은 카드 × 첫 카드 토큰"의 전체 예상도 출력한다. 재개 실행은 예산을 새로 세고, 이전 실행의 비용은 이력에 남는다. 불명 과금 건수는 추정에 포함하지 않고 따로 표시한다.
- 키: 환경 변수 `TYPESAFE_API_KEY`, 없으면 `~/.config/typesafe/api_key`. 파일 권한이 소유자 외에 열려 있으면(`mode & 0o077`) 읽지 않고 멈춘다. 둘 다 없으면 안내만 출력하고 종료 코드 2. 키는 출력 가능한 ASCII(0x21~0x7E)만 허용한다. 줄바꿈·제어 문자가 섞이면 네트워크 전에 거부한다(그대로 보내면 `http.client`의 `ValueError`가 키를 traceback에 담는다. 구현 검수 1회차 지적). 네트워크 호출 전에 검사한다.
- 마지막 안전망: `main()`은 예상 못 한 예외도 키 문자열을 지운 한 줄로만 stderr에 쓰고 종료 코드 2로 끝난다. traceback 전체를 찍지 않는다. 그 경로에서 `inflight`는 지우지 않는다(요청이 나갔는지 모르므로 다음 실행이 불명으로 센다).
- 전송 루프가 어떤 예외로든 끊기면(`KeyboardInterrupt` 포함) 그때까지의 시도 통계를 `jev.json`에 남기고 `stopped: "interrupted"`로 표시한 뒤 다시 던진다. SIGKILL은 막지 못한다.

## 7. 시험 계획(`python3 -m unittest discover -s tests`, 네트워크·실제 키·실제 대기 없음)

경계별로 묶는다. 건수는 목표가 아니다. 기대값은 손으로 계산한 값이고 구현식을 복제하지 않는다. 전송은 `urlopen` 함수가 아니라 `jev.py`가 쓰는 opener 경계를 대역으로 바꾼다.

1. **변환과 가격 출력**: 손으로 만든 확률표로 보간값(예: 9,900원에서 0.6, 12,900원에서 0.4이면 11,400원), 정확히 0.5, 첫 점부터 미만(아래쪽 검열), 끝까지 미달(위쪽 검열), 두 번 교차(첫 교차 + `multi_cross`), 단일 교차 비단조(0.9, 0.7, 0.8, 0.4 → `nonmonotone`만), 평탄 구간, 순서 보정. 변환 결과를 실제 `read → analyse → report`에 넣어 채택 수·제외 수·통화·검열 안내를 확인. 완전한 답 4장이면 가격 절만 "표본 부족"이고 다른 절은 나옴. 사다리: 6.5 × 0.2 = 1.3 소수 유지, `--ladder-max` 2.0·3.0·무한대 거부, `--price` 0·음수·NaN 거부. 깨진 응답(질문 누락, 보기 밖 choice, 확률 합 1.2, 음수 확률, 1 초과, NaN, 다른 `model`, 빈 `model`)이 거부되고 파일이 생기지 않음.
2. **지문·디렉터리 상태**: 같은 ID의 소득만 바꾼 카드, seed, 통화, 변환 버전, `--price` 변경이 호출 전에 거부. 불완전 디렉터리(`panel.json`만 없음), `jev.json` 없는 답 폴더, 현재 카드 밖 JSON, 손상 답이 모두 호출 전에 거부. 기존 패널 디렉터리에 `--n`을 주면 거부. `markets` 고객 거부.
3. **저장과 재개**(가짜 전송): 카드 10장. 파일이 `.tmp` 없이 생김. 답 파일 교체 직전·직후, `jev.json` 교체 직전·직후에 중단을 주입하고, 확정 저장된 장수만큼 건너뛰어 나머지만 보내는지(기대 호출 수를 확정 장수로 적음). 응답 수신 뒤 저장 전 중단은 `inflight`를 통해 "처리 여부 불명 1"로 이력에 남음. 2회차 실행은 호출 0건. 카드별 보기 순서가 건너뛴 카드 수와 무관. `answers/`·`panel.json`·`personas.json`·`results.md`가 바이트 단위로 그대로.
4. **전송·비용**: 429 → 200이면 2회 호출과 대기값(숫자형·HTTP 날짜형·잘못된 `Retry-After`), 529 재시도, 재시도 소진 뒤 종료 코드 2, 401은 재시도 없음, 깨진 200은 재시도 없음, 302는 후속 요청 0건, 잘못된 `usage`는 거부, 키 부재 안내, 644 권한 키 파일 거부, 가짜 키가 stdout·stderr·파일 어디에도 없음, 누적 비용 기준 `--budget-usd` 중단, 재개 실행의 이력 누적.
5. **집계와 판정 분리**: `panel.tally(d, answers="jev-answers")` 분해 표. `jev-results.md/json`이 1~6절을 모두 냄. 에이전트 답 0건이면 `agreement: null`. 에이전트 `results.json`은 `jev run` 전후로 같음. `compile.verdict`는 `jev-results.json`이 있어도 같은 판정(25% 경계 양쪽 사례 1개씩).
6. **회귀**: 기존 `tests/` 전부. `tally(d)` 기본 경로가 4.6 변경 뒤에도 같음. `reason: ""`인 에이전트 답이 있는 기본 경로도 같음.
7. **고정 응답 재생**: 2026-10-27 사용자 승인 뒤 최종 틀로 HabitNav 카드 20장(`founder/panel`, seed 7)을 실제 호출했다(요청 20건, 재시도 0, 입력 토큰 48,418, $0.0020, 5초). 답 파일 20개를 `tests/fixtures/jev/`에 두었다(키 없음, 페르소나 본문 없음. 확률·가격·플래그만). 시험은 파일의 확률에서 답을 다시 만들어 같은지 보고(결정성), 실제 `read → analyse`를 이 폴더에 돌려 아래 황금값과 비교한다. 황금값(실제 실행 출력에서 옮겨 적음): 구매 1/20(P015), 평균 확률 0.3655, 이유 trust 9 / habit 5 / quality 3 / price 2 / timing 1, 가격 n 20·dropped 0·PMC 3,180원·OPP 3,180원·IPP 11,190원·PME 18,300원, 검열 too_cheap 아래 20·too_expensive 위 5, 비단조 cheap 3·expensive 2·too_cheap 1, 복수 교차 0, 보정 0. 같은 카드의 에이전트 패널과 2×2: 둘 다 구매 1(P015) / 에이전트만 2(P007·P019) / Jev만 0 / 둘 다 아님 17.

실제 확인 결과는 위 7번에 적었다. 2절의 `exp2` 수치(IPP 10,680원)와 최종 틀(IPP 11,190원)의 차이는 틀·사다리 변경과 실행 간 변동이 섞인 값이다.

## 8. 정해야 할 것(기본값으로 진행한다. 바꾸려면 말해 주세요)

1. Jev는 판정에 들어가지 않는다. 판정은 에이전트 패널만.
2. 질문은 고정 틀 + `--paid/--price/--unit`. 결과를 본 뒤 문구를 바꾸지 않는다.
3. 검열값은 경계값으로 저장하고 곡선별 수를 가격 절에 함께 보인다. 가격 절 제목은 "탐색 추정". 대안(카드 제외)은 남는 카드를 너무 줄인다.
4. 다중 시장 패널은 1차 미지원(요청 전 거부).
5. 공개 저장소에 포함. 키는 포함하지 않는다. DESIGN.md 원칙 4에 예외를 적는다.

## 9. 보장하지 못하는 것

- Jev 확률·상위 카드·가격이 실제 고객 행동과 맞는지 검증한 자료가 없다. 페르소나 시뮬레이션은 Jev의 설계 용도가 아니다. HiddenLayer는 Jev도 LLM으로 보인다고 보고했다.
- 같은 제품의 작은 오퍼 차이(±0.03)는 실행 간 변동(0.01)과 문구·질문 묶음 차이(0.02~0.05)에 묻힌다.
- 가격 곡선은 요금제가 하나인 피치 20장에서만 형식을 확인했다. 검열값은 편향을 만든다. 곡선별 수를 보고할 뿐 없애지 못한다. 가격 절은 확정 범위가 아니다.
- 모델 버전이 바뀌면 같은 카드도 답이 바뀐다. 지문이 다른 실행은 섞이지 않는다.
- 응답 전에 끊긴 요청의 과금 여부는 모른다. `--budget-usd`는 추정 기반이다.
- 100명 에이전트 패널의 판정 정밀도를 대신하지 않는다.
