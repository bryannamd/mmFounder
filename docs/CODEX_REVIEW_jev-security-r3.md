위 표의 해소는 아래 가짜 응답과 로컬 재현 범위에 대한 판단이다. 전체 시험 통과가 모든 수신 실패 조건의 안전성을 뜻하지는 않는다.

## 새 지적 목록

높음 0건, 중간 0건, 낮음 1건이다. 아래 항목은 새로 확인한 잔여 조건이며, 이번 수정이 새로 만든 회귀는 아니다.

### R3-L1. 심각도 낮음 | skills/founder-consumer/jev.py:483 | 짧게 끝난 오류 본문도 완전한 본문으로 취급한다

- 문제: `len(body) < ERROR_MAX`이면 `_show()`가 본문을 출력한다. 하지만 표준 `http.client.HTTPResponse.read(4096)`은 고정 길이 응답이 조기 EOF로 끝났을 때 4,096바이트보다 적은 데이터를 반환할 수 있다. 이 경로에서는 선언된 `Content-Length` 미달만으로 `IncompleteRead`가 발생하지 않는다. 따라서 짧은 반환값이 완전한 본문이라는 보장은 없다. `_clean()`의 `jev.py:447` 주석도 이 경우에는 맞지 않는다.
- 시나리오: 2회차와 동일하게 `_key_ok()`가 허용하는 300자 가짜 키를 30번 반복한 9,000바이트 오류 본문을 준비했다. 401 응답은 `Content-Length: 9000`을 선언하지만 3,500바이트만 전송하고 끝난다. 가짜 소켓의 바이트를 실제 `HTTPResponse`로 파싱한 뒤 실제 `run` 경로에 공급했다. 요청 1회, 종료 2였으며 stderr에 키 접두사 157자가 남았다. 받은 데이터에는 완전한 키 11개와 다음 키의 앞 200자가 있다. 완전한 키를 치환하면서 마지막 조각이 300자 발췌 범위로 당겨진다. 원래 준비한 본문은 완전한 키의 반복뿐이다.
- 영향과 판단: 키 전체와 해당 접두사는 stdout 및 생성 파일에는 없었다. 응답 객체는 닫혔다. 긴 키와 키 반사 오류 응답, 조기 종료가 함께 필요하다. 실제 서비스의 키 길이와 이런 응답 동작은 확인하지 않았으므로 낮음으로 판정한다. 2회차의 정확한 4,096바이트 절단 조건은 해결됐지만, 모든 잘린 오류 본문에서 키 조각이 사라졌다고 볼 수는 없다.
- 제안: 가장 단순한 해결은 HTTP 오류 본문 발췌를 생략하고 상태 코드와 고정 설명만 출력하는 것이다. 진단을 유지한다면 읽기 상한뿐 아니라 응답 완결성도 확인하고, 완결성을 확인하지 못한 본문은 표시하지 않는다. 위 조기 EOF 조건을 회귀 시험에 추가한다. `Content-Length` 확인만으로 모든 전송 방식의 완결성을 보장한다고 설명해서는 안 된다.
- 근거: `/tmp/jev-security-r3.ko4_5qzj/early_eof.py`, `early_eof.log`. 실제 네트워크와 실제 키는 사용하지 않았으며 로그에는 가짜 키 자체 대신 길이와 노출 여부만 기록했다.

## 수정 영향과 13.2절 판단

- HTTP 오류 응답 종료: `jev.py:473`과 `:490`에서 헤더와 `Retry-After`를 읽은 다음 `finally`에서 응답을 닫는다. 숫자 7초, HTTP 날짜 7초, 잘못된 값의 기본 대기 1.5초, 600초 입력의 상한 60초가 유지됐다. 각 응답은 다음 대기 전에 닫혔으며 재시도 본문은 읽지 않았다. 503의 6회 실패에서도 응답 6개가 모두 닫히고 시도 6회·재시도 5회가 보존됐다.
- `fp` 부재와 읽기 실패: 헤더와 `fp`가 모두 `None`인 `HTTPError`로 302·401의 고정 오류, 429·529의 재시도 성공을 확인했다. `AttributeError`는 없었다. 본문 읽기가 `IncompleteRead`를 내는 경우도 응답을 닫고 부분 본문을 출력하지 않았다. 실제 `HTTPResponse` 객체를 사용한 302·401·429에서도 응답과 입력 스트림이 닫혔다. R3-L1은 예외 없이 짧게 반환되는 별도 경로다.
- 연결 진단의 키 제거: 보통 길이, 따옴표·역슬래시 포함, 300자 가짜 키를 원문·문자열 repr·바이트 repr·JSON 표현으로 오류 사유에 넣었다. 최종 실패의 진단은 키가 제거된 한 줄이었고, 파일과 stdout으로 문장이 넘어가지 않았다. 일시적인 연결 오류 뒤 성공하거나 마지막 응답이 401이면 앞선 연결 오류 문장도 출력되지 않았다. CONNECT 요청에는 가짜 API 키가 없었다.
- 리다이렉트 진단 유지: 출처·불신 자료 표시, 키 제거, 길이 제한, stderr 한정이라는 조건에서 원인 확인용 출력은 수용할 수 있다. 리다이렉트를 따르거나 결과 문서에 저장하는 동작과 구분된다. 이 판단이 외부 문장을 실제 에이전트가 항상 무시한다는 보장은 아니다.
- `_save_answer()`의 임시 파일 재읽기 유지: 기존 `panel._answer_ok()`가 경로를 받으며 직렬화된 결과를 검사하므로, 이를 유지한 판단은 수용한다. 메모리 검증으로 바꾸려면 같은 검사 조건을 보존하는 별도 변경이 필요하다. 재읽기를 없애는 것이 이번 보안 수정의 필수 조건은 아니다.
- `results()` 재읽기 보류: 이번 수정 범위에서 보류한 판단은 수용하되, 기존 낮음 결함은 남는다. 검증 직후 관련 없는 답 하나를 추가한 2회차 재현을 반복하니 종료 0인데 `cards=2`, `price.complete=3`이었다. `jev.py:715`, `:725`의 디스크 재읽기를 이미 검증한 `saved` 기반 집계로 바꾸는 후속 정리가 타당하다.
- 받아들인 제한: 0600은 `_write()`로 생성하는 파일의 권한이며 원본 `panel.py` 파일과 폴더 전체의 비공개를 보장하지 않는다. 새 패널 생성 시 키를 먼저 읽는 `run` 분기는 외부 ID를 읽는 분기와 다르다. sweep의 답 폴더 링크 차단은 해당 변형에 적용된다. 실행 중 폴더 교체 경쟁, 전체 수신 시간 상한 부재, 상한 초과 응답의 비용 불명은 기존에 공개한 제한으로 유지할 수 있다. 이번 변경이 이를 해결했다고 보지는 않는다.
